Distributed optimization · AISTATS 2017

Train together. Keep data apart.

Federated Averaging moves computation to many devices: each client improves a shared model locally, then a server combines the resulting models. The central trade-off is not just accuracy—it is useful progress per communication round.

Communication-Efficient Learning of Deep Networks from Decentralized Data · H. Brendan McMahan, Eider Moore, Daniel Ramage, Seth Hampson & Blaise Agüera y Arcas

1 · Prerequisite bridge

A shared recipe, many private kitchens.

Ordinary training imagines data gathered in one place, where batches update one model. Federated learning changes where the calculation happens: the data stays with many clients, while a shared model visits them in rounds.

Concrete analogy

Imagine a cooking class where every kitchen keeps its own ingredient notebook. The instructor sends the same recipe draft to a selection of kitchens. Each kitchen tries several revisions using only its own notes, then reports the revised recipe—not the notebook—to the instructor. The instructor makes a size-weighted blend and starts the next round.

The boundary matters: a model update is not the raw dataset, but it can still reveal information. The paper describes privacy advantages from reducing data centralization; it does not claim that model averaging by itself guarantees privacy.

2 · The setting

Communication, not arithmetic, is the scarce resource.

The paper describes client data that is non-IID (one client’s examples need not resemble the population) and unbalanced (clients may have very different amounts of data). Mobile devices may also be offline or bandwidth-limited. Sending a model back and forth repeatedly can dominate the cost.

Failed baseline: Federated SGD can take one local gradient step, communicate, then repeat. It is straightforward, but it can require many communication rounds. FedAvg asks whether clients can safely do more local training before the next aggregation.

This leaves a tension: more local work can reduce messages, but clients can drift toward their unlike-local objectives before their models are averaged.

3 · The actors and notation

Separate the global objective from each client’s view.

There are K clients. Client k owns an index set Pk with nk examples; n is the total number of examples. Each client has a local objective Fk(w), while the server aims to minimize the data-size-weighted global objective:

f(w)=∑k=1KnknFk(w)
C

Client fraction. The proportion selected for a round. The paper selects m = max(CK, 1) clients.

E

Local epochs. How many passes a selected client makes through its data before returning a model.

B

Local batch size. The minibatch used in each local update. Smaller batches usually mean more local update steps.

These are levers for spending more computation at the edge in exchange for fewer server rounds. They do not remove the difficulty of heterogeneous data.

4 · The mechanism

Federated averaging is local SGD plus a carefully weighted merge.

  1. Select: choose m clients and send each the same current model wt.
  2. Update locally: each selected client splits its own data into batches and performs E local epochs of SGD, producing wt+1k.
  3. Aggregate: the server weights each returned model by that client’s example count, rather than giving a one-example client the same influence as a large client.
wt+1=∑k=1Knknwt+1k

5 · Worked traces

Calculate the merge before you trust the slogan.

Trace A · Example-count weighting

Two selected clients start from the same scalar model. After their local training, client A has nA = 2 examples and returns wA = 4; client B has nB = 8 examples and returns wB = 10.

wnext=210×4+810×10=8.8

Interpretation: the server does not average to 7. Each model is weighted by the amount of client data it represents. This is the model-averaging form of combining example-weighted gradients in FedSGD.

Trace B · More local work, fewer possible messages

A client has nₖ = 120 examples. With E = 3 local epochs and minibatches of B = 20, the paper’s local-update count is:

uk=EnkB=3×12020=18 local updates

FedSGD’s matching endpoint is E = 1, B = ∞: one full-batch local gradient calculation before communicating. FedAvg deliberately lets each selected client make many updates, which can save rounds but can magnify client drift.

Predict before reveal · Which returned model pulls the server farther?

Client A always has nA = 2, wA = 4; client B returns wB = 10. Move B’s example-count slider and predict the new global model.

Static reading: with B holding 8 examples, the aggregate is 8.8. With B holding 2 examples, the aggregate is 7.0. Data-size weighting changes the server’s result even though neither client’s local model has changed.

What this evidence supports

In these controlled CIFAR-10 experiments, the listed FedAvg configuration reached those target accuracies with far fewer communication rounds than the baselines. It does not show universal superiority for all client distributions, models, client availability patterns, or privacy risks.

The paper also reports that very large numbers of local epochs can plateau or diverge on the Shakespeare task (Figure 3, PDF p. 7). More local computation is a lever to tune, not a monotone rule.

7 · Boundaries and misconceptions

Data staying local is not the same as being private.

Misconception: FedAvg sends each client’s raw dataset to the server.

No. In the paper’s formulation, the client computes a model update locally and returns that update for aggregation. This minimizes raw-data centralization, but it does not prove updates reveal nothing about data.

Misconception: averaging many trained models always makes a good model.

No. The paper explicitly notes that parameter-space averaging can be arbitrarily bad for general non-convex objectives. Its practical success depends in part on clients beginning from a common current global model and taking limited local updates.

Misconception: non-IID only means clients have unequal amounts of data.

They are different. Unbalanced describes differing dataset sizes. Non-IID describes differing data distributions: for example, a particular user’s language or labels may not represent the overall population.

Misconception: the 2017 paper’s method is a full modern production privacy system.

No. The paper identifies differential privacy and secure multiparty computation as future directions. Production systems can add secure aggregation, privacy accounting, client eligibility rules, robustness defenses, and many other choices beyond this core algorithm.

8 · Active recall

Rebuild the round without looking back.

  1. What stays with a client in the paper’s federated-learning setup?

    Its local training dataset. The selected client receives the global model, trains locally, and returns an update/model for server aggregation.

  2. Why weight returned models by nₖ/n?

    It lets each local model contribute in proportion to the number of examples represented, matching the global example-weighted objective.

  3. What do C, E, and B control?

    C controls the fraction of selected clients, E the number of local epochs, and B the local minibatch size.

  4. Why can extra local epochs be useful and dangerous?

    They can reduce communication rounds by doing more work between messages, but on heterogeneous clients they can make local models drift and can hurt convergence.

  5. State one paper result without overclaiming it.

    For its CIFAR-10 configuration, Table 3 reports FedAvg reaching 85% test accuracy in 2,000 rounds versus 99,000 for the SGD baseline. That is a scoped experimental communication-round comparison, not a general privacy or deployment guarantee.

9 · Connect it to your mental map

FedAvg changes where optimization occurs, not what a gradient is.

Adam and SGD

SGD describes one parameter update. FedAvg orchestrates many local SGD updates and then averages their resulting parameters. Optimizer choice and federation are separate layers.

Batch normalization

BatchNorm estimates statistics from a batch. Federated learning exposes a new question: when data distributions differ by client, which local statistics or updates can be safely combined? This paper focuses on averaging model updates, not solving normalization under heterogeneity.

DPO and post-training

DPO defines a preference-based loss; FedAvg is a training topology. In principle, a learning objective and a decentralized optimizer can be composed, but this paper’s evidence is about supervised experiments, not preference training.

AlphaGo

AlphaGo spends extra local compute to reduce an impossible search. FedAvg spends extra device-side compute to reduce communication. Both make a constrained resource explicit, but one is deliberation at inference time and the other is optimization during training.

10 · Takeaway

A federated round is a compromise between local adaptation and global agreement.

Clients work where their data lives; the server turns their differently sized local progress into one shared next model. FedAvg’s lasting idea is to trade cheap local computation for expensive communication—while remembering that non-IID data, update leakage, and overly long local training prevent that trade from being automatic.
